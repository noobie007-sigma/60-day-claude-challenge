Foundations of Scalability

Why systems break under load, and the vocabulary you need before designing anything.

What "Scale" Actually Means Concept

A system that works perfectly for 10 users can fall over completely at 10 million. Scalability is a system's ability to handle increasing load — more users, more data, more requests per second — without a proportional collapse in performance. It's not about being fast at one moment; it's about staying fast (or degrading gracefully) as demand grows.

Two numbers matter more than any others in this field:

  • Latency — how long a single request takes (milliseconds per request).
  • Throughput — how many requests the system handles per unit time (requests/second).

You can often trade one for the other. Batching requests can raise throughput while raising the latency of any individual request. Good system design is choosing the right trade-off for the actual use case, not chasing one metric blindly.

Analogy — The Restaurant Kitchen. Latency is how long it takes to cook one plate. Throughput is how many plates the kitchen sends out per hour. A kitchen can be fast for one order (low latency) but collapse when 200 orders arrive at once (low throughput) if it has only one chef and one stove. Scaling means adding chefs, stoves, or a smarter order queue — not just working faster.

Vertical vs Horizontal Scaling Comparison

Vertical scaling (scale up) means making one machine more powerful — more CPU, RAM, faster disks. Horizontal scaling (scale out) means adding more machines and distributing load across them.

DimensionVertical ScalingHorizontal Scaling
How it worksUpgrade a single server's hardwareAdd more servers behind a load balancer
CeilingHard physical/cost limitNear-limitless (add more boxes)
ComplexityLow — no architecture changeHigher — needs load balancing, statelessness
Fault toleranceSingle point of failureOne node failing doesn't take the system down
Cost curveExponential at the high endRoughly linear with commodity hardware
Common Misconception. "Just add more servers" is not automatically horizontal scaling done right. If your app stores session data in local memory on one server, a request landing on a different server won't find that session — you must design for statelessness (e.g. shared session store) before horizontal scaling works correctly.

✏ Exercise — Diagnose the Bottleneck

An e-commerce API has average latency of 40ms at 50 req/s, but 900ms at 400 req/s, on a single server with 4 CPU cores. What's most likely happening, and what's the fastest fix that doesn't require a full re-architecture? Write your answer, then reveal the model answer.

The server is saturated — requests are queuing faster than they're processed, so tail latency explodes (a classic queueing effect, not a code bug). The fastest fix without re-architecting is vertical scaling (bigger instance) or adding 1-2 more identical servers behind a basic load balancer (horizontal scaling) — both buy time before a deeper redesign (caching, query optimization) is needed.

KEY TAKEAWAYS

  • Scalability is about sustaining performance as load grows, not raw speed at one instant.
  • Latency (time per request) and throughput (requests per time) are different, sometimes competing, metrics.
  • Vertical scaling is simple but capped; horizontal scaling is limitless but requires statelessness and coordination.
  • Response time doesn't degrade linearly — it explodes past a saturation point due to queueing.

Load Balancing & Caching

Distributing traffic intelligently, and avoiding redundant work with caching.

Load Balancing Algorithms Concept

A load balancer sits in front of your servers and decides which server handles each incoming request. The algorithm it uses matters:

AlgorithmHow it decidesBest for
Round RobinCycles through servers in orderUniform servers, uniform request cost
Least ConnectionsSends to the server with fewest active connectionsLong-lived or variable-length requests
Weighted Round RobinRound robin, but stronger servers get more trafficMixed hardware capacity
IP HashSame client always → same serverSession affinity ("sticky sessions")
Analogy — Supermarket Checkout Lines. Round robin is a queue that sends every third customer to the same register regardless of basket size. Least connections is a helpful attendant who always points you to the shortest line. Sticky sessions is being loyal to the cashier who already knows your loyalty card is scanned.

Caching Strategies Concept

A cache stores the result of expensive work (a DB query, a computation) in fast memory so future requests skip the expensive path. The two things to get right are where data lives and when it gets invalidated.

  • Cache-aside (lazy loading): app checks cache first; on a miss, reads from DB and populates the cache.
  • Write-through: every write goes to the cache and the DB simultaneously, keeping them in sync.
  • TTL (time-to-live): cached data expires automatically after N seconds, bounding staleness.
  • Eviction (LRU): when the cache is full, the Least Recently Used entry is discarded first.
Common Misconception. Caching is not "always faster and safe to add anywhere." It introduces staleness risk — if the underlying data changes and the cache isn't invalidated correctly, users can see outdated information. Cache invalidation is famously one of the two hardest problems in computer science for a reason.

✏ Exercise — Pick the Strategy

A news site shows article view counts that update roughly every few minutes; exact real-time precision doesn't matter. Which caching approach fits best, and why?

Cache-aside with a short TTL (e.g. 60 seconds) is ideal here. View counts tolerate slight staleness, so you avoid the complexity of write-through synchronization while still cutting nearly all DB reads for a hot article.

KEY TAKEAWAYS

  • Load balancer algorithm choice should match the traffic pattern (uniform vs variable-length requests).
  • Cache-aside is the most common general-purpose strategy; write-through trades write latency for consistency.
  • TTL and LRU eviction bound how stale or how large a cache can get.
  • Caching adds a consistency risk that must be deliberately managed, not ignored.

Databases at Scale

Indexing, replication, and sharding — how storage keeps up with everything else.

SQL vs NoSQL Comparison

SQL (Relational)NoSQL
SchemaFixed, strict schemaFlexible / schema-less
ConsistencyStrong (ACID transactions)Often eventual consistency
Scaling styleTypically vertical, sharding is harderBuilt for horizontal scaling
Best forRelational data, financial recordsHigh-velocity, semi-structured data
ExamplesPostgreSQL, MySQLMongoDB, DynamoDB, Cassandra
Analogy — Filing Cabinets vs Sticky Notes. SQL is a filing cabinet with strict labeled folders — great for structured, related records, but rigid to reorganize. NoSQL is a wall of sticky notes — fast to add in any shape, easy to scale across many walls, but harder to guarantee everything is perfectly cross-referenced.

Indexing Concept

An index is a separate, sorted data structure that lets the database find rows without scanning the entire table. Without an index, looking up a user by email means checking every row — a full table scan.

Indexes speed up reads dramatically but slow down writes slightly (every insert must also update the index) and use extra disk space — index the columns you query most, not everything.

Replication Concept

Replication keeps copies of the database on multiple machines. The most common pattern is primary-replica: all writes go to one primary, which streams changes to read replicas that serve read traffic — increasing read throughput and adding redundancy.

Common Misconception. Replication is not automatically the same as backup. A replica mirrors changes in near real-time — if bad data or a bug corrupts the primary, that corruption propagates to replicas too. You still need separate point-in-time backups.

Sharding Concept

Sharding splits one huge table across multiple databases (shards), each holding a subset of rows — typically by a shard key like user ID range or a hash of the ID. This lets writes scale horizontally too, unlike simple replication, but joins across shards become expensive or impossible, and choosing a bad shard key can create "hot shards" that get disproportionate traffic.

✏ Exercise — Choose a Shard Key

You're sharding a social media "posts" table. Sharding by created_date means almost all writes today hit one shard. Propose a better shard key and explain why.

Shard by a hash of user_id (or post ID). This spreads writes evenly across shards regardless of when posts are created, avoiding the "hot shard" problem where all current traffic lands on a single shard.

KEY TAKEAWAYS

  • SQL favors strong consistency and structure; NoSQL favors flexible schema and horizontal scale.
  • Indexes turn slow full-table scans into fast lookups, at the cost of write overhead and storage.
  • Replication scales reads and adds redundancy; it is not a substitute for backups.
  • Sharding scales writes by splitting data, but a poorly chosen shard key creates hot spots.

Designing the Complete System

Combining scalability, load balancing, caching, and data scaling into one coherent architecture.

The System Design Interview Framework Practical

Whether in an interview or on the job, a repeatable process prevents you from freezing on a blank page:

  1. Clarify requirements — functional (what must it do) and non-functional (scale, latency, availability targets).
  2. Estimate scale — back-of-envelope math: users, requests/sec, storage growth per day.
  3. Sketch the high-level architecture — clients → load balancer → services → cache → database.
  4. Deep-dive the bottleneck — the single component most likely to fail under the estimated load.
  5. Address trade-offs — consistency vs availability, cost vs redundancy.

Worked Example — Designing a URL Shortener Example

Requirements: shorten a long URL, redirect on visit, handle 100M new URLs/month and far more reads than writes (read-heavy).

Reasoning: since reads vastly outnumber writes, a cache-aside layer in front of the database absorbs most redirect traffic. The database is sharded by a hash of the short code to spread both storage and write load evenly, and replicated for durability. A base62 encoded auto-incrementing ID or hash generates short codes, and the load balancer uses round robin since all API servers are identical and stateless.

Availability vs Consistency Concept

The CAP theorem states a distributed system facing a network partition (P) must choose between Consistency (C) and Availability (A) — it cannot fully guarantee both. In practice: CP systems (e.g. many SQL clusters) reject requests rather than return stale data; AP systems (e.g. many NoSQL stores) keep responding but may briefly return outdated data.

Analogy — Two Bank Tellers, No Phone Line. If two tellers at different branches can't communicate during an outage, they can either both refuse withdrawals until they can confirm the balance together (consistent, but unavailable) or both allow withdrawals and reconcile later (available, but risking a temporary overdraft). CAP forces this exact choice.

✏ Exercise — Full Design Sketch

Sketch (in words) an architecture for a ride-sharing app's "find nearby drivers" feature, which needs low-latency reads, frequent location updates, and can tolerate slightly stale driver positions. Mention your choice of load balancing, caching, and database strategy.

Driver locations update frequently, so store current position in an in-memory cache (e.g. Redis with geospatial indexing) rather than the primary DB, using a short TTL so stale drivers age out automatically. Use least-connections load balancing since matching requests vary in cost. Persist trip and driver profile data in a replicated SQL database for consistency, but keep the hot "current location" path entirely in the cache layer to meet the low-latency requirement.

KEY TAKEAWAYS

  • Every design starts with requirements and scale estimation before drawing boxes.
  • Read-heavy systems lean on caching; write-heavy systems lean on sharding.
  • The CAP theorem forces an explicit choice between consistency and availability during a network partition.
  • There is no single "correct" architecture — only one that's justified by the requirements.

Final Practical Challenge

Bring together every module into one design.

Challenge — Design "SnapVote": A Live Polling App

SnapVote lets creators post a poll; up to 2 million people can vote on a single popular poll within minutes of it going live, and everyone should see near real-time updated results. Design the full system:

  1. Estimate the read/write ratio and peak requests/second.
  2. Choose a load balancing strategy and justify it.
  3. Decide what gets cached, and which caching strategy (cache-aside, write-through, TTL) fits vote counts.
  4. Decide SQL vs NoSQL for votes, and whether/how you'd shard or replicate.
  5. State one explicit consistency vs availability trade-off you're making, and why.
Scale: 2M votes over ~10 minutes ≈ 3,300 writes/sec at peak; reads (poll result views) likely 10-50x that.

Load balancing: Round robin across stateless API servers, since each vote/read request is roughly uniform cost.

Caching: Vote *counts* (not individual votes) are cached with a short TTL (e.g. 1-2 seconds) or updated via write-through into an in-memory counter (e.g. Redis INCR) — this absorbs the huge read volume on results without hammering the database on every view.

Database: A NoSQL store (or a SQL table sharded by poll ID) for raw vote records, since writes are simple appends with no complex joins needed; shard by poll ID so one viral poll's writes are isolated to a subset of shards, then scale by adding more shards for hot polls.

Trade-off: Choose availability over strict consistency for the *displayed* vote count — showing a count that's 1-2 seconds stale is acceptable, but rejecting valid votes during a spike is not.

Cheat Sheet & Continued Learning

Quick Reference Cheat Sheet

Scaling

Vertical = bigger machine, simple, capped.
Horizontal = more machines, needs statelessness, near-limitless.

Load Balancing

Round Robin = uniform traffic.
Least Connections = variable-length requests.
IP Hash = sticky sessions.

Caching

Cache-aside = default choice.
Write-through = need cache/DB in sync.
TTL/LRU = bound staleness and size.

Databases

Index = fast reads, slower writes.
Replication = scale reads + redundancy (not backup!).
Sharding = scale writes, watch for hot shards.

Summary Notes

System design is the discipline of matching architecture to real constraints: expected scale, read/write ratio, consistency requirements, and cost. There is rarely one "correct" answer — only designs that are well-justified against the specific requirements at hand. The core levers you now have are: scaling the compute layer (vertical/horizontal), distributing traffic (load balancing), avoiding repeated expensive work (caching), and scaling data storage (indexing, replication, sharding) — all balanced against the CAP theorem's consistency/availability trade-off.
